1 How it works

Deployer does two things:

  • Hosts your static site — upload a .zip, it gets served at /sites/<name>/.
  • Captures form submissions — any HTML form posting to /submit/<site>/<form-name> gets appended to a per-form .csv and .json file. Fields are auto-discovered, no schema needed.

The Dashboard shows live counts, and each site has a real-time submissions view.

2 Prepare your project

Your project should be a folder containing index.html at the root, plus any assets (CSS, JS, images). For example:

my-landing/ ├── index.html ├── about.html ├── thanks.html ├── styles/ │ └── main.css ├── scripts/ │ └── app.js └── images/ └── logo.png

Use relative paths in your HTML (styles/main.css, not /styles/main.css) so they resolve correctly under /sites/<name>/.

4 Zip & deploy

Create a .zip of the project folder. Deployer accepts both shapes:

  • Folder-wrapped: my-landing.zip contains my-landing/index.html. The wrapper is unwrapped automatically.
  • Flat: my-landing.zip contains index.html at the root.

macOS: right-click the folder → Compress. To skip .DS_Store noise, use the terminal:

cd path/to/parent
zip -r my-landing.zip my-landing -x "*.DS_Store" "__MACOSX/*"

Linux / WSL:

zip -r my-landing.zip my-landing

Windows: right-click the folder → Send to → Compressed (zipped) folder.

Then on the Dashboard: drop the .zip into the upload box, give it a name (e.g. my-landing), and click Deploy site. Your site goes live at /sites/my-landing/.

5 Add a form

Point any HTML <form> at /submit/<site>/<form-name>. Every named input is captured, plus a timestamp and the submitter's IP.

<form action="/submit/my-landing/contact" method="POST">
  <label>Name    <input name="name" required></label>
  <label>Email   <input type="email" name="email" required></label>
  <label>Message <textarea name="message"></textarea></label>

  <!-- optional: redirect after submit -->
  <input type="hidden" name="_redirect" value="thanks.html">

  <button type="submit">Send</button>
</form>

Want a JSON API instead? Post JSON and you'll get a JSON response:

await fetch('/submit/my-landing/contact', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email, message })
});
// → { ok: true }

Multiple forms per site are fine — pick a different <form-name> for each (e.g. contact, newsletter, survey). Each gets its own CSV/JSON file.

6 View submissions live

Open a site from the Dashboard. The submissions table refreshes every few seconds — new rows fade in and the count updates without a page reload. Look for the Live indicator in the top right of the table.

Each form row is also written to two files on disk:

  • submissions/<site>/<form>.json — one JSON object per line (JSONL, easy to stream).
  • submissions/<site>/<form>.csv — header auto-extends when a new field appears.

Use the Download CSV button on the site page to pull the data, or read the file directly.

7 Live shared state (datasets)

Forms are append-only — perfect for capture, not for editing. When you need shared state that all visitors can read and update (issue trackers, to-do lists, polls, RSVP lists, etc.), use the datasets API instead.

Each dataset is a list of items identified by a server-generated id, with a rev counter that bumps on every change so clients can poll cheaply. One-click deploy the bundled Production issues tracker example from the dashboard to see it in action.

Endpoints (no auth — anyone with the URL can read/write):

GET    /data/<site>/<dataset>/items[?since=<rev>]
   → { changed, rev, items: [...] }
   (when since == rev, body is just { changed:false, rev } — cheap polling)

POST   /data/<site>/<dataset>/items
   body: { ...your fields, _actor?: "name" }
   → 201 { item, rev }

PATCH  /data/<site>/<dataset>/items/<id>
   body: { ...fields to merge, _actor?: "name" }
   → 200 { item, rev }

DELETE /data/<site>/<dataset>/items/<id>
   → 200 { rev }

Minimal client — paste into any page deployed under /sites/<site>/:

const SITE = location.pathname.split('/')[2];     // "/sites/<name>/" → name
const API  = '/data/' + SITE + '/issues/items';

let rev = -1;
async function load() {
  const r = await fetch(API + (rev < 0 ? '' : '?since=' + rev));
  const d = await r.json();
  if (d.changed === false) return;
  rev = d.rev;
  render(d.items);                                  // ← your render fn
}
async function add(fields)        { await fetch(API,           { method:'POST',  headers:{'Content-Type':'application/json'}, body: JSON.stringify(fields) }); load(); }
async function update(id, fields) { await fetch(API+'/'+id,    { method:'PATCH', headers:{'Content-Type':'application/json'}, body: JSON.stringify(fields) }); load(); }
async function remove(id)         { await fetch(API+'/'+id,    { method:'DELETE' }); load(); }

setInterval(load, 2000);
load();

Reserved fields are stripped from your input and managed by the server: id, _ts (created), _updated, _created_by, _updated_by. Pass _actor: "your name" on writes to attribute changes.

Storage: data/<site>/<dataset>.json on disk (atomic writes, per-file lock for concurrent requests). Persists across re-deploys — deleting the site does not delete the dataset.

8 Tips & gotchas

  • Naming. Site and form names must be lowercase letters, digits, dashes or underscores (1–50 chars).
  • Re-deploy. Uploading the same site name overwrites the previous files. Submissions are kept (they live in submissions/, not sites/).
  • Redirect after submit. Add <input type="hidden" name="_redirect" value="thanks.html"> to send users to your own thank-you page (relative to your site root).
  • Size limit. 50 MB per upload by default. Adjust MAX_UPLOAD_BYTES in app.py if you need more.
  • Production. The built-in dev server is fine for local testing — for real deployments, run behind gunicorn or uwsgi and put a reverse proxy in front.
