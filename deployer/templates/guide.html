1 How it works

Deployer does two things:

  • Hosts your static site — upload a .zip, it gets served at /sites/<name>/.
  • Captures form submissions — any HTML form posting to /submit/<site>/<form-name> gets appended to a per-form .csv and .json file. Fields are auto-discovered, no schema needed.

The Dashboard shows live counts, and each site has a real-time submissions view.

2 Prepare your project

Your project should be a folder containing index.html at the root, plus any assets (CSS, JS, images). For example:

my-landing/ ├── index.html ├── about.html ├── thanks.html ├── styles/ │ └── main.css ├── scripts/ │ └── app.js └── images/ └── logo.png

Use relative paths in your HTML (styles/main.css, not /styles/main.css) so they resolve correctly under /sites/<name>/.

4 Zip & deploy

Create a .zip of the project folder. Deployer accepts both shapes:

  • Folder-wrapped: my-landing.zip contains my-landing/index.html. The wrapper is unwrapped automatically.
  • Flat: my-landing.zip contains index.html at the root.

macOS: right-click the folder → Compress. To skip .DS_Store noise, use the terminal:

cd path/to/parent
zip -r my-landing.zip my-landing -x "*.DS_Store" "__MACOSX/*"

Linux / WSL:

zip -r my-landing.zip my-landing

Windows: right-click the folder → Send to → Compressed (zipped) folder.

Then on the Dashboard: drop the .zip into the upload box, give it a name (e.g. my-landing), and click Deploy site. Your site goes live at /sites/my-landing/.

5 Add a form

Point any HTML <form> at /submit/<site>/<form-name>. Every named input is captured, plus a timestamp and the submitter's IP.

<form action="/submit/my-landing/contact" method="POST">
  <label>Name    <input name="name" required></label>
  <label>Email   <input type="email" name="email" required></label>
  <label>Message <textarea name="message"></textarea></label>

  <!-- optional: redirect after submit -->
  <input type="hidden" name="_redirect" value="thanks.html">

  <button type="submit">Send</button>
</form>

Want a JSON API instead? Post JSON and you'll get a JSON response:

await fetch('/submit/my-landing/contact', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email, message })
});
// → { ok: true }

Multiple forms per site are fine — pick a different <form-name> for each (e.g. contact, newsletter, survey). Each gets its own CSV/JSON file.

6 View submissions live

Open a site from the Dashboard. The submissions table refreshes every few seconds — new rows fade in and the count updates without a page reload. Look for the Live indicator in the top right of the table.

Each form row is also written to two files on disk:

  • submissions/<site>/<form>.json — one JSON object per line (JSONL, easy to stream).
  • submissions/<site>/<form>.csv — header auto-extends when a new field appears.

Use the Download CSV button on the site page to pull the data, or read the file directly.

7 Live shared state (datasets)

Forms are append-only — perfect for capture, not for editing. When you need shared state that all visitors can read and update (issue trackers, service status boards, to-do lists, polls, RSVP lists, etc.), use the datasets API instead.

Each dataset is a list of items identified by a server-generated id, with a rev counter that bumps on every change so clients can poll cheaply. One-click deploy the bundled Production issues tracker example from the dashboard to see it in action.

All endpoints (no auth — anyone with the URL can read/write):

GET    /data/<site>/<dataset>/items[?since=<rev>]
   → { changed, rev, items: [...] }
   (when since == rev: { changed:false, rev } — no payload, cheap poll)

POST   /data/<site>/<dataset>/items
   body: { ...your fields, _actor?: "name" }
   → 201 { item, rev }

POST   /data/<site>/<dataset>/seed
   body: { items: [...], key?: "fieldName", mode?: "init"|"upsert"|"replace" }
   → { seeded, updated, skipped, rev, items }

PATCH  /data/<site>/<dataset>/items/<id>
   body: { ...fields to merge, _actor?: "name" }
   → 200 { item, rev }

DELETE /data/<site>/<dataset>/items/<id>
   → 200 { rev }

DELETE /data/<site>/<dataset>/items
   → 200 { cleared, rev }          ← clears ALL items

Reserved fields — stripped from client input, managed by server:

id  ·  _ts (created at)  ·  _updated  ·  _created_by  ·  _updated_by. Pass _actor: "name" on writes to attribute changes.

Pattern: hardcoded master data → live shared state

If your page already has a hardcoded JS array (services, teams, SLAs, SVC list…) and you want to add live mutable fields on top (status, notes, owner…), use the seed endpoint to push that array into a dataset once, then let all users read and update it in real time.

Three seed modes:

  • mode: "init" (default) — seeds only when the dataset is empty. The first user to load the page populates it; everyone else just reads the live state. Safe to call on every page load.
  • mode: "upsert" — merges by a key field (e.g. "name" or "service_id"). New master entries are added; existing ones get their master-data fields refreshed without overwriting mutable fields like status. Use this when the master list grows over time.
  • mode: "replace" — clears all items and re-seeds from scratch. Use for a full reset (e.g. a hard master-data change). All live edits are lost.

Complete example — service status board:

<!-- index.html — paste just before </body> -->
<ul id="svc-list"></ul>

<script>
// ── Master data (hardcoded, owned by you) ─────────────────────────────────
const MASTER = [
  { name: 'Payment Gateway', team: 'Payments',  sla: '99.9%' },
  { name: 'Auth Service',    team: 'Platform',  sla: '99.95%' },
  { name: 'Notifications',   team: 'Comms',     sla: '99.5%' },
  // add more services here — upsert mode keeps live edits intact
];

// ── Deployer wiring ───────────────────────────────────────────────────────
const SITE    = location.pathname.split('/')[2];   // works on any deploy
const API     = '/data/' + SITE + '/services/items';
const SEED_EP = '/data/' + SITE + '/services/seed';

let rev = -1;

// Seed master data into the dataset.
// mode "upsert" + key "name": adds new services, refreshes master fields,
// never overwrites live fields (status, notes) that users have edited.
async function seedMaster() {
  await fetch(SEED_EP, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ items: MASTER, key: 'name', mode: 'upsert' })
  });
}

async function load() {
  const r = await fetch(API + (rev < 0 ? '' : '?since=' + rev));
  const d = await r.json();
  if (d.changed === false) return;
  rev = d.rev;
  render(d.items);
}

async function setStatus(id, status) {
  const actor = localStorage.getItem('actor') || 'unknown';
  await fetch(API + '/' + id, {
    method: 'PATCH',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ status, _actor: actor })
  });
  load();
}

function esc(s) {
  return String(s ?? '').replace(/&/g,'&amp;').replace(/</g,'&lt;')
                         .replace(/>/g,'&gt;').replace(/"/g,'&quot;');
}

function render(items) {
  const STATUS_COLOR = { running:'green', degraded:'orange', down:'red' };
  document.getElementById('svc-list').innerHTML = items.map(it => `
    <li>
      <strong>${esc(it.name)}</strong> · ${esc(it.team)} · SLA ${esc(it.sla)}
      <span style="color:${STATUS_COLOR[it.status] || 'gray'}">
        ${esc(it.status || 'unknown')}
      </span>
      <button onclick="setStatus('${esc(it.id)}','running')">Running</button>
      <button onclick="setStatus('${esc(it.id)}','degraded')">Degraded</button>
      <button onclick="setStatus('${esc(it.id)}','down')">Down</button>
      ${it._updated ? '<small>Updated ' + esc(it._updated) + ' by ' + esc(it._updated_by) + '</small>' : ''}
    </li>
  `).join('');
}

// On load: seed master data, then start live polling.
seedMaster().then(() => {
  load();
  setInterval(load, 2000);
});
</script>

How it works end-to-end:

  • First user opens the page → seedMaster() calls the seed endpoint with mode:"upsert" → services are written to the dataset with status: undefined.
  • Any user clicks a status button → PATCH updates just that field → rev bumps → all other open tabs pick it up within 2 s.
  • You add a new service to the MASTER array and redeploy → next page load, seedMaster() inserts the new entry without touching existing statuses.
  • To fully reset: change mode to "replace" in seedMaster(), deploy once, then change it back to "upsert".

Storage: data/<site>/services.json on disk (atomic writes, per-file lock). Persists across re-deploys — deleting the site does not delete the dataset.

8 Tips & gotchas

  • Naming. Site and form names must be lowercase letters, digits, dashes or underscores (1–50 chars).
  • Re-deploy. Uploading the same site name overwrites the previous files. Submissions are kept (they live in submissions/, not sites/).
  • Redirect after submit. Add <input type="hidden" name="_redirect" value="thanks.html"> to send users to your own thank-you page (relative to your site root).
  • Size limit. 50 MB per upload by default. Adjust MAX_UPLOAD_BYTES in app.py if you need more.
  • Production. The built-in dev server is fine for local testing — for real deployments, run behind gunicorn or uwsgi and put a reverse proxy in front.
